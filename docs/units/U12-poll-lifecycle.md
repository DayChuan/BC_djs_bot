# A. 截止前提醒

## 規格（2026-09-03 使用者確認）

| 項目 | 內容 |
|---|---|
| 時機 | 截止前 **12 小時**與 **3 小時**，共兩次 |
| 重複 | **每個時間點只發一次**。bot 重啟還原時不能重發 |
| 對象 | `noticeRoles.poll` 那個身分組的成員，**扣掉**已投票的、**扣掉**在投票訊息上按了 ❎ 的 |
| 沒人要提醒時 | **完全不發訊息**（不要發「大家都投完了」，那也是洗版） |
| 發在哪 | 投票所在的頻道（開了討論串就是那個討論串） |

## ❎ 的判斷方式

`:negative_squared_cross_mark:` ＝ **❎（U+274E）**，按在**投票的公開訊息**上。

**不需要監聽 `messageReactionAdd`**：提醒時間到才去把訊息抓下來、讀那顆表情的使用者清單就好。

```js
const message = await channel.messages.fetch(poll.messageId)
const reaction = message.reactions.cache.get('❎')
const users = reaction ? await reaction.users.fetch() : new Map()
```

這樣做的好處是**沒有狀態要維護**——不必記誰按了、誰又取消了，看的永遠是當下的實況。
`GuildMessageReactions` intent 與 `Partials.Message/Reaction` 都早就開著了（`src/main.js`），
但抓下來的 reaction 可能是 partial，讀 `users` 前要先 `fetch()`。

**發布投票時 bot 要自己先按一個 ❎**，否則沒有人知道有這個機制。
按完之後那顆表情的使用者清單裡會有 bot 自己，計算時要濾掉。

## ⚠️ 開工第一件事：先實測「鎖定的討論串能不能按表情」

U10 的討論串是**鎖定**的。鎖定明確會擋「發訊息」，但**會不會連加表情一起擋掉，我沒有把握**。

**在寫任何程式之前，先請使用者用一般成員帳號去現有的測試討論串按一個表情。**

- **按得下去** → 照上面的設計做
- **按不下去** → ❎ 這條路整個不通，改成在投票的個人面板上加一顆「我這次不參與」按鈕，
  狀態寫進投票紀錄。功能一樣，只是入口不同。**不要硬試表情**

這一項先確認再動手，順序反過來會白寫一半。

## 排程與重啟

兩個時間點各自一個排程 key：

```
poll:remind12:<pollId>
poll:remind3:<pollId>
```

用現成的 `scheduler.scheduleAt()`。投票紀錄加一個欄位記已經發過哪幾次：

```js
reminded: {h12: true, h3: false}
```

`restorePolls()` 重掛排程時：**已經發過的不再掛、時間點已經過去的也不要補發**
（重啟後補一則三小時前該發的提醒只會讓人困惑）。舊資料沒有 `reminded` 欄位就當成都沒發過。

## 提及的長度上限

一則訊息 2000 字元，一個提及約 22 字元，所以**大約 80 人就會爆**。
超過就分則發送，或改成只提及身分組並附一句「還沒投的有 N 位」。實作時擇一，寫進決策紀錄。

# B. 討論串滿 30 天自動刪除

## 規格

| 項目 | 內容 |
|---|---|
| 條件 | **結算後滿 30 天**（不是「最後活動時間」，見下） |
| 對象 | 只刪**我們自己開的**投票討論串 |
| 時機 | 開機時跑一次，跟現有的 `pollArchive.purgeExpired()` 一起 |
| 保留期 | 寫進 `src/config/polls.js`，跟 `ARCHIVE_RETENTION_DAYS` 放一起 |

**為什麼不用「最後活動時間」**：討論串是鎖定的，沒有人能發言，
最後活動時間永遠停在 bot 發訊息那一刻，拿它當條件等於沒有條件。

## ⚠️ 這個單元最危險的一行

刪之前**必須**確認那真的是討論串：

```js
if(!channel.isThread()) return   // 沒有這一行就會刪掉正式頻道
```

沒開討論串的投票，它的 `channelId` 是**正式的文字頻道**。少這個判斷就是把頻道刪掉，
而且 Discord 的頻道刪除**救不回來**。

建議再加一道：只處理歸檔紀錄裡 `thread === true` 的場次，跟 `isThread()` 兩道一起擋。

刪除失敗（權限不足、已經被人手動刪掉）一律**吞掉只記 log**，不要讓開機流程中斷。

## 驗收

**單元測試**（不得 import discord.js，所以名單計算要抽成純函式）：

1. 身分組 10 人、投了 3 人、按 ❎ 2 人 → 待提醒 5 人
2. 全部投完 → 待提醒 0 人（呼叫端據此不發訊息）
3. bot 自己按的 ❎ 不算在扣除名單裡，也不會被提醒
4. 同一人既投票又按 ❎ → 只扣一次，不會變成負數或重複
5. `reminded` 欄位不存在的舊紀錄 → 當成兩次都沒發過
6. 已經發過的時間點不再重掛排程
7. 討論串保留判定：結算滿 30 天為真、29 天為假

**實機（測試伺服器）：**

8. 發一場截止時間設在 13 小時後的投票 → 訊息上有 bot 按的 ❎
9. 把截止時間改到 12 小時內 → 提醒發出，**只提及沒投也沒按 ❎ 的人**
10. 同一場再等到 3 小時的時間點 → 第二次提醒發出，內容更新
11. 兩次提醒之間重啟 bot → **不會重複發**，也不會漏掉還沒到的那次
12. 全部人都投完或按 ❎ → **完全不發訊息**
13. 手動把某場歸檔紀錄的日期改成 31 天前再重啟 → 那個討論串被刪除，log 有紀錄
14. **把一場沒開討論串的投票也改成 31 天前 → 它的文字頻道毫髮無傷**（這條最重要）
