# 0. `raid` 開關（2026-09-04 併入）

## 為什麼

原本 ❎ 與截止前提醒是「只要不是快速投票就做」，名單是「身分群組是不是楓之谷」。
兩個閘門不一致，而且**一般投票（臨時問大家吃什麼）也會被按上 ❎、被 tag**，那是純噪音。

改成一個明確的開關 `raid`（組隊模式），**一次控制三件事**：

| | `raid: false`（預設） | `raid: true` |
|---|---|---|
| 結算後出隊伍名單（U11） | ✗ | ✓ |
| bot 按 ❎ | ✗ | ✓ |
| 截止前提醒沒投票的人 | ✗ | ✓ |

**刻意不用「身分群組是不是楓之谷」推斷**：身分群組管的是「顯示哪個職業選單」，
跟「要不要編隊」是兩件事。綁在一起的話，想開一場楓之谷投票但不要名單、
或想讓別的群組也編隊，都表達不出來。

名單那一段仍然**額外**檢查身分群組必須是楓之谷——編隊規則寫死那六個職業，
沒有這道檢查就會拿 TRPG 的角色去湊箭神與聖騎士。

## 設定的地方

跟 `thread` 完全一樣：**模板詳情面板一顆切換按鈕 ＋ `/poll` 一個選填參數**。
平常用「楓之谷週常」模板的話，在模板上開一次就永久生效。

舊的投票紀錄沒有 `raid` 欄位 = 關閉（`wantsRaid()` 收斂成布林）。

# A. 截止前提醒

## 規格（2026-09-03 使用者確認）

| 項目 | 內容 |
|---|---|
| 時機 | 截止前 **12 小時**與 **3 小時**，共兩次 |
| 重複 | **每個時間點只發一次**。bot 重啟還原時不能重發 |
| 對象 | `noticeRoles.poll` 那個身分組的成員，**扣掉**已投票的、**扣掉**在投票訊息上按了 ❎ 的 |
| 沒人要提醒時 | **完全不發訊息**（不要發「大家都投完了」，那也是洗版） |
| 發在哪 | 投票所在的頻道（開了討論串就是那個討論串） |

## ❎ 的判斷方式

`:negative_squared_cross_mark:` ＝ **❎（U+274E）**，按在**投票的公開訊息**上。

**不需要監聽 `messageReactionAdd`**：提醒時間到才去把訊息抓下來、讀那顆表情的使用者清單就好。

```js
const message = await channel.messages.fetch(poll.messageId)
const reaction = message.reactions.cache.get('❎')
const users = reaction ? await reaction.users.fetch() : new Map()
```

這樣做的好處是**沒有狀態要維護**——不必記誰按了、誰又取消了，看的永遠是當下的實況。
`GuildMessageReactions` intent 與 `Partials.Message/Reaction` 都早就開著了（`src/main.js`），
但抓下來的 reaction 可能是 partial，讀 `users` 前要先 `fetch()`。

**發布投票時 bot 要自己先按一個 ❎**，否則沒有人知道有這個機制。
按完之後那顆表情的使用者清單裡會有 bot 自己，計算時要濾掉。

## ✅ 開工第一件事（已完成）：鎖定的討論串能不能按表情

U10 的討論串是**鎖定**的。鎖定明確會擋「發訊息」，但會不會連加表情一起擋掉，事前無法確定，
所以先請使用者實測再動手。

**2026-09-03 實測結果：可以按。**照原設計走 ❎，不改成按鈕。

實測時確認的是「一般成員點得動訊息上已經存在的那顆 ❎」。
**「加一顆全新的表情」沒有單獨驗證** —— 因為 bot 發布時會自己先按好一顆，
成員永遠只需要點現成的，這個差別不影響設計。日後若把「bot 先按」拿掉，這一項要重測。

投票訊息本身就發在討論串裡（`sendPollMessage()` 把 `channelId` 換成討論串 id），
不是發在母頻道再開串，所以這個前提確實成立。

## 排程與重啟

兩個時間點各自一個排程 key：

```
poll:remind12:<pollId>
poll:remind3:<pollId>
```

用現成的 `scheduler.scheduleAt()`。投票紀錄加一個欄位記已經發過哪幾次：

```js
reminded: {h12: true, h3: false}
```

`restorePolls()` 重掛排程時：**已經發過的不再掛、時間點已經過去的也不要補發**
（重啟後補一則三小時前該發的提醒只會讓人困惑）。舊資料沒有 `reminded` 欄位就當成都沒發過。

## 提及的長度上限

一則訊息 2000 字元，一個提及約 22 字元，所以**大約 80 人就會爆**。
超過就分則發送，或改成只提及身分組並附一句「還沒投的有 N 位」。實作時擇一，寫進決策紀錄。

# B. 討論串滿 30 天自動刪除

## 規格

| 項目 | 內容 |
|---|---|
| 條件 | **結算後滿 30 天**（不是「最後活動時間」，見下） |
| 對象 | 只刪**我們自己開的**投票討論串 |
| 時機 | 開機時跑一次，跟現有的 `pollArchive.purgeExpired()` 一起 |
| 保留期 | 寫進 `src/config/polls.js`，跟 `ARCHIVE_RETENTION_DAYS` 放一起 |

**為什麼不用「最後活動時間」**：討論串是鎖定的，沒有人能發言，
最後活動時間永遠停在 bot 發訊息那一刻，拿它當條件等於沒有條件。

## ⚠️ 這個單元最危險的一行

刪之前**必須**確認那真的是討論串：

```js
if(!channel.isThread()) return   // 沒有這一行就會刪掉正式頻道
```

沒開討論串的投票，它的 `channelId` 是**正式的文字頻道**。少這個判斷就是把頻道刪掉，
而且 Discord 的頻道刪除**救不回來**。

建議再加一道：只處理歸檔紀錄裡 `thread === true` 的場次，跟 `isThread()` 兩道一起擋。

刪除失敗（權限不足、已經被人手動刪掉）一律**吞掉只記 log**，不要讓開機流程中斷。

## 決策紀錄

- 2026-09-04　`isThreadExpired()` 的比較用 `<=` 而不是 `<`。「滿 30 天」＝已經過了 30 天，用 `<` 的話剛好整整 30 天那一筆要多等一天才刪，測試「驗收 7」抓到的就是這個。

- 2026-09-04　`scheduleReminders()` 的 raid 閘門放在函式**裡面**而不是呼叫端。理由：`restorePolls()` 是無條件呼叫的，只擋發布那一處的話，bot 每重啟一次就會把非組隊投票的提醒重新掛回去，而且要等提醒真的發出去才會有人發現。
- 2026-09-04　新增 `raid` 開關，一次控制名單／❎／提醒三件事。使用者決定：這三件事只有固定團的每週揪團才用得到。
- 2026-09-04　**不把楓之谷拉成獨立指令**。理由：它需要的參數跟一般投票幾乎一樣（標題、選項、模板、每週四參數、身分、多角色、討論串…），拆出去等於複製 15 個參數，以後每修一個 bug 要改兩個地方，而差別只有三個布林行為。
- 2026-09-04　`raid` 不從 `identityGroup` 推斷。理由：身分群組管的是選單顯示，與編隊是兩件事；綁在一起就無法表達「楓之谷但不要名單」。
- 2026-09-04　名單仍額外要求身分群組是楓之谷。理由：編隊規則寫死那六個職業，少這道檢查會拿別的群組的角色去湊。

- 2026-09-03　B1 與 B3 合成一個單元。理由：都是「投票發出去之後到消失為止」的維護動作，動同一批檔案。
- 2026-09-03　提醒時間點為截止前 12 小時與 3 小時，各發一次。使用者指定。
- 2026-09-03　不參與的表達方式用在投票訊息上按 ❎（U+274E）。使用者指定。
- 2026-09-03　**不監聽 `messageReactionAdd`**，提醒時才抓訊息讀當下的表情清單。理由：沒有狀態要維護，也不會因為漏接事件而算錯。
- 2026-09-03　發布時 bot 自己先按一個 ❎。理由：不先按的話沒有人知道有這個機制。
- 2026-09-03　扣完沒有人就完全不發訊息。使用者指定：發「大家都投完了」也是洗版。
- 2026-09-03　討論串的判定用「結算後滿 30 天」。理由：討論串是鎖定的，最後活動時間永遠停在 bot 發訊息那一刻。
- 2026-09-03　刪討論串前必須 `isThread()` ＋ 歸檔紀錄的 `thread === true` 兩道防護。理由：沒開串的投票，`channelId` 是正式頻道，刪掉救不回來。
- 2026-09-03　實測確認一般成員在**鎖定的討論串**裡點得動已存在的 ❎，故 A 案照原設計走表情，不改按鈕。bot 發布時先按一顆（使用者：「大家比較方便」）。
- 2026-09-03　**兩道防護不是等價的，第 2 道才是真正擋災難的那一道。** 開串失敗會退回母頻道（`openPollThread()` 的既有行為），那種場次紀錄上 `thread` 仍然是 `true`、`channelId` 卻是正式文字頻道 —— 只有 `channel.isThread()` 分得出來。第 1 道的作用是「連抓都不要去抓」，不能拿它當唯一防線。對應測試：`pollArchive.test.js` 的「紀錄上 thread=true 但頻道不是討論串 → 絕對不刪」。
- 2026-09-03　`purgeThreads()` 排在 `purgeExpired()` **之前**。理由：歸檔紀錄一旦被 90 天清理刪掉，就再也不知道哪些頻道是我們開的討論串，那些串會永遠留著。
- 2026-09-03　提及長度上限採**分則發送**，不採「只提及身分組 ＋ 還沒投的有 N 位」。理由：後者會把已經投過的人也叫一次，而這個功能的重點正是只吵還沒表態的人。
- 2026-09-03　`allowedMentions` 用 `{parse: ['users']}` 而不是列舉 `users` 清單。理由：`users` 欄位上限 100 人，超過整則會被 Discord 退回；`parse: ['users']` 只放行訊息裡的個人提及，一樣不會誤 tag 身分組或 @everyone。
- 2026-09-03　先 `markReminded()` 再發訊息。理由：反過來的話，發到一半當機會在下次重啟時整串重發；重複洗版比漏發一次嚴重。
- 2026-09-03　「投過票」的定義是**至少選了一個選項**，空白登記不算。理由：跟 `tally()` 一致，否則會出現「結算報表上沒有他、卻也不提醒他」的黑洞。
- 2026-09-03　快速投票（`type === 'quick'`）不掛提醒、也不按 ❎。理由：它是語音現場用的，壽命只有幾分鐘，提醒時間點必定已過，多一顆表情只是噪音。
