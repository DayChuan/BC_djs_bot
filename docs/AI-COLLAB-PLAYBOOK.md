# 人＋多個 AI 的協作模式

這份文件描述一套**已經在實務中跑出來**的協作方式：一個人類負責決策與驗收，
一個 AI 當專案經理，多個 AI 當工程師，一次做一個單元。

**它不綁任何特定專案。** 要用在新專案，把這個檔複製過去，照最後一節的「導入步驟」做。

---

## 一、三種角色

| 角色 | 是誰 | 負責 | **不做** |
|---|---|---|---|
| **決策者** | 人類 | 提需求、做取捨、實機驗收、`git push`、跑所有指令 | 不寫程式、不記細節 |
| **專案經理（PM）** | 一個 AI 對話 | 把需求轉成單元檔、審查、驗收、寫交辦指令、維護總表 | **不實作功能**（除非是跨單元的小修正） |
| **工程師** | 每個單元各一個 AI 對話 | 照單元檔實作、寫測試、更新自己的單元檔 | **不 push、不決定規格、不碰別人的檔案** |

### 為什麼要有 PM 這一層

工程師的對話會愈長愈笨，而且它只看得到自己那個單元。有一個橫向的角色才能：

- 發現**同一個規則有兩個入口**（最容易產生的 bug 類型）
- 發現**兩個單元的檔案領域重疊**
- 記得三週前為什麼做了某個決定
- 用同一套標準驗收，不會這個單元嚴、那個單元鬆

### 權限分工的鐵則

**只有人類能執行改變外部狀態的動作。** AI 一律做到 commit 為止：

- AI **不 push**、不部署、不重啟服務、不刪資料
- AI 要跑的指令，寫成步驟給人類代跑，並說明「預期會看到什麼」
- AI 判斷不了的事（例如「按鈕在鎖定的討論串裡能不能按」）**設計一個實驗請人類跑**，
  不要用推論當結論

---

## 二、需求怎麼進來：交接文件

人類把新想法寫成一份 **Handover 文件**放進 `docs/Functions/`，格式不拘，通常包含：
任務背景、核心運作邏輯、資料結構、限制與注意事項。

PM 讀完之後**不直接實作**，而是：

1. 對照現有程式碼，判斷**可行性**
2. 指出交接文件**沒寫、但一定會出事**的地方
3. 提出規劃與取捨，**列出需要人類決定的問題**
4. 人類回答後，才寫成單元檔

> 這一步是整套流程裡價值最高的。交接文件通常是「理想中的做法」，
> 而它跟現有程式碼的落差、以及沒考慮到的邊界，正是專案會出事的地方。
>
> 實例：一份交接文件寫「每 1～2 秒編輯一次訊息更新倒數」，
> 照做會撞上平台的速率限制。PM 在動工前就指出來，改成「用戶端自己算倒數」，
> 編輯次數從每分鐘 30 次降到 4 次。

**原始的交接文件不要改。** 它是需求的歷史紀錄，決策的演變寫在單元檔裡。

---

## 三、單元檔：這套流程的核心

一個功能 = 一個單元 = 一個檔案 `docs/units/UXX-<名稱>.md`。

### 固定結構

```markdown
# UXX　單元名稱

狀態：可開工 | 進行中 | 待驗收 | 完成 | 擱置
進度：3/8
依賴：U03（已完成）
可平行：可 / 不可與 UXX（兩者都改同一個檔）
工作目錄：<完整絕對路徑>
來源：docs/Functions/xxx.md

## 目標          一句話說完
## 為什麼要做    不寫這段，三週後沒人記得
## ⚠️ 一定會出事的地方   ← 最重要的一節
## 不做的事      明確劃界，防止範圍膨脹
## 相關檔案      三類：要改的／要新增的／只讀但一定要看的
## 進度          - [ ] XX-1 …（做完打勾）
## 驗收          單元測試項目 ＋ 實機步驟，逐條可勾
## 決策紀錄      日期＋決定＋**理由**
```

### 三個讓它真的有用的細節

**① 「相關檔案」要寫到工程師不用瀏覽整個專案。**
每個檔案標明「在哪、做什麼、要不要改」，只讀的檔案還要寫「你需要知道的事」。
這是壓縮 token 的關鍵，也讓新對話能立刻進入狀況。

**② 「決策紀錄」一定要寫理由。**
只寫決定，之後的人會「順手改掉」。實例：

> 冰雷取等級最高、黑騎取等級最低進一隊。**這是刻意不對稱的，不是筆誤，不要統一。**

**③ 「⚠️ 一定會出事的地方」由 PM 在動工前寫。**
這一節寫的是「照直覺做會踩到什麼」，例如：平台的速率限制、
資料格式相容、權限邊界、刪除類操作的防護。工程師會照著避開。

### 已完成的單元

移進 `docs/units/done.md`，只留**結論與 commit hash**，單元檔本身刪掉。
平常不需要讀它，只有「當初為什麼這樣做」才翻。總表因此永遠只有正在進行的東西。

### 還沒成形的想法

放 `docs/units/BACKLOG.md`，每項要有「為什麼」與「已知的坑」。
不要讓它變成願望清單——寫不出「為什麼」的就不要記。

---

## 四、總表

`docs/PLAN.md` 只是一張儀表板，**不放細節**：

```markdown
| 單元 | 內容 | 狀態 | 進度 | 依賴 | 可平行 |
```

加上「現在可以同時開的」與「等待使用者決定的」兩段。
**總表由 PM 維護**，工程師不要改（平行時必衝突）。

---

## 五、交辦：給工程師的開工指令

PM 產出一段可以直接複製貼上的指令。固定包含：

1. **工作目錄的完整絕對路徑**，並點名容易搞混的鄰近目錄
2. **只讀兩份文件**：協作規範（`CLAUDE.md`）＋ 它負責的單元檔。
   明講「不要瀏覽整個專案」
3. **這個專案踩過的坑**（一到三條，跟這個單元相關的）
4. **規則清單**（見下）
5. 結尾固定是：「先讀完那兩份文件，然後告訴我你打算怎麼做 XX-1，等我同意再動手」

### 規則清單（每次都附）

- 不開分支、不切換分支（見下方「共用工作目錄」）
- 只動單元檔宣告的「檔案領域」，要碰別的先停下來問
- commit 前先 `git status --short`，用具名 `git add <檔案>`，**不要用 `-A` 或 `.`**
- commit 訊息只寫一行，理由寫進單元檔的決策紀錄
- 每個進度項目做完就停，列出「改了什麼」與「怎麼驗證」，等確認再往下
- 動手前先講要改什麼，等同意
- 測試怎麼跑、哪裡不能跑
- **你只做到 commit，push 由人類手動執行**

## 六、平行作業

多個工程師同時進行時，隔離手段**只有一個**：各單元宣告的「檔案領域」不重疊。

### ⚠️ 共用工作目錄就不要開分支

如果所有 AI 對話**共用同一個工作目錄**（常見於網路磁碟或單一開發機）：

**不要開分支、不要 checkout。** git 的分支是綁在工作目錄上的——A 切走的瞬間，
B 腳下的檔案也跟著換掉，而 B 不會知道，後續的 commit 會全部落在 A 的分支上。

> 實際發生過：一條線開了 `unit/U03-state` 分支，另一條線的 commit 全部落在那上面，
> 人類 `git push origin test` 得到 `Everything up-to-date`，找不到自己的東西。

同理，`git add -A` 會掃到別條線還沒 commit 的檔案。**一律具名 add。**

### 兩個單元不得不碰同一個檔案時

PM 在**兩邊的交辦指令裡都寫明**：「動這個檔案前先 `git status --short`，
有別人未 commit 的改動就先回報」。

## 七、驗收

### 誰驗什麼

| 類型 | 誰 | 怎麼做 |
|---|---|---|
| 單元測試 | 人類代跑，PM 判讀 | 純邏輯層，要能離線測 |
| 程式碼審查 | PM | 讀 diff，找「同一規則多個入口」「邊界條件」「未處理的失敗」 |
| 執行紀錄 | PM | 讀 log，找錯誤、也找**該出現卻沒出現**的訊息 |
| 實機驗收 | 人類 | 照單元檔的清單逐條做 |

### 三個實務上學到的事

**① 權限相關的驗收，一律用一般帳號。**
用管理員帳號驗權限等於沒驗——管理員繞過大部分限制。
這個坑踩過兩次，第二次是功能上線後使用者回報才發現。

**② 「log 上什麼都沒有」也是重要證據。**
使用者回報按鈕沒反應，而後端一筆錯誤都沒有 → 代表請求根本沒送到後端，
問題在前端／平台那一層，不是程式的錯。**這個推論省下了往錯方向查的時間。**

**③ AI 判斷不了的事，設計實驗給人類跑。**
不要用推論當結論。實例：

> 「鎖定的討論串能不能按按鈕？我沒有把握。
> **在寫任何程式之前**，請用一般成員帳號去按一個試試。
> 按得下去 → 照 A 設計做；按不下去 → 改用 B。這一步不確認就動手，會白寫一半。」

## 八、AI 的行為準則

這幾條放進 `CLAUDE.md` 之類的常駐規範裡：

1. **不要過多臆測。** 推論要標明依據；靜態分析的結論要標**信心程度**，
   無法確認的就說無法確認
2. **給單一方案，不要並列多種選項。** 直接選一個最合適的，一句話說明為什麼。
   真有必須由人類決定的分歧才提問，且限縮在兩個選項以內
3. **一次只做一個步驟**，做完停下來，列出「改了什麼」與「怎麼驗證」
4. **錯了就直說。** 判斷錯誤時明確講「我上一則說的是錯的」，
   不要含糊帶過——含糊會讓人類繼續照錯的方向走
5. **寫註解要寫「為什麼」不是「做什麼」。** 尤其是繞過某個坑的程式碼，
   要寫清楚不寫的話會發生什麼

## 九、導入步驟（新專案）

1. 複製這份 `AI-COLLAB-PLAYBOOK.md` 過去
2. 建立 `CLAUDE.md`（或等價的常駐規範），至少寫：
   - 這個目錄是什麼、哪裡可以執行程式、哪裡不行
   - 環境架構（開發／測試／正式）與部署方式
   - 上面第八節的行為準則
   - 單元制的規則（第五節的規則清單）
3. 建立 `docs/PLAN.md` 空總表、`docs/units/`、`docs/units/BACKLOG.md`、`docs/Functions/`
4. 第一次跟 PM 對話時說：
   > 請照 `docs/AI-COLLAB-PLAYBOOK.md` 的模式，你當專案經理。
   > 先讀 `CLAUDE.md`，盤點現有程式碼，把待辦拆成單元檔並給我總表。
5. 之後每個功能：丟 Handover → PM 評估可行性 → 你做決定 → PM 寫單元檔 →
   PM 給交辦指令 → 你開新對話貼給工程師 → 工程師做完 → 你 push、驗收 → PM 結案

---

## 十、這套流程解決了什麼

| 常見問題 | 這套流程怎麼處理 |
|---|---|
| 對話變長之後 AI 開始亂改 | 一個單元一個對話，每個對話只讀兩份文件 |
| 「三週前為什麼這樣寫」沒人記得 | 決策紀錄，含理由 |
| AI 熱心地順手改掉別的東西 | 檔案領域 ＋「要碰別的先問」 |
| 需求邊做邊長大 | 單元檔的「不做的事」 |
| 同樣的坑一直踩 | 「一定會出事的地方」＋ 常駐規範裡的技術重點 |
| 平行作業互相踩踏 | 不開分支 ＋ 具名 add ＋ 檔案領域 |
| AI 說「應該可以」然後不行 | 信心標示 ＋ 設計實驗請人類實測 |
